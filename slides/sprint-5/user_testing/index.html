User testing session

A short test for GlobalData Healthcare, made up of search and filter tasks in an interactive HTML prototype.

GlobalData × Shoreditch · 5 October 2026

Context

As part of our design engagement, we are working with GlobalData Healthcare to prototype directions for advanced search in the Drugs database, built around natural-language input.

This session tests a revised prototype, which carries the fixes from the previous round of testing, against the previous round's prototype. Both run the same tasks, so the outcomes compare directly.

Three user goals

From 176,404 existing advanced searches across the Drugs and Clinical Trials databases, we narrowed the work down to three user goals.

G1
Quick search
53% of searches use a single filter and 85% use three or fewer. A usable list has to be reachable in very few steps.
G2
Refined search
80% of follow-up searches keep the same fields and change a value. Only 12% add a filter. Adjusting a known query has to be fast and reversible.
G3
Power search
15% of searches use four or more filters, with up to 22 in one search. OR within a field appears in 19%, NOT in under 1%.
The fixes in the revised prototype make building a result set easier than in the previous round's prototype. Across the seven tasks it should average a higher ease score, and a higher recommendation score.
Hypothesis

Questions

01
Find every Phase III drug available in Europe that works on Janus Kinase. (G1)
The previous round's first task, unchanged. The search returns 50 drugs.
02
Using the search just built, swap Europe for the United States. (G2)
The previous round's lowest-scoring task, now with values that are replaced rather than added. The search returns 33 drugs.
03
Get results for a set of five filters, using plain language. (G3)
Marketed, oral, small molecule, United States, and any receptor-based mechanism of action. A plain sentence resolves all five and returns 12 drugs.
04
Get the same set of results by choosing each filter by hand, without typing a sentence. (G3)
The task does not name the advanced filter, so the account of how it was done shows whether the builder can be found unprompted.

Each task is followed by an ease score from 1 to 5 and the reason for it.

Questions, continued

05
Take route of administration out of the search, so drugs given any way are included. (G2)
Removing a filter that has been added. The list grows from 12 drugs to 28.
06
Narrow the list down to the drugs of one company. (G2)
The 28 results span 16 companies. The task does not say how, so the reasons show where testers reach first.
07
Search for Phase I gene therapies for dermatology in Brazil, and change the search until it finds results.
The full query matches nothing in either prototype, so the task tests recovery from an empty result.
08
How likely is a recommendation of this way of searching to a colleague?
Scored from 0 to 10, with the reason for the score.

Instructions

01
One link per tester
Each tester uses the prototype link they are given. The two links open different prototypes with identical tasks.
02
What is being tested
How a set of results is built: writing a search, checking and changing the filters it picks, and choosing filters by hand. The test assesses the design, not the tester.
03
How tasks are scored
Each task is scored for ease from 1, Very difficult, to 5, Very easy, straight after it is done. The final question runs from 0, Not at all likely, to 10, Extremely likely.
04
This is a prototype
The drug data is a sample and only some paths are built. Where something does not respond, a note of what was expected is the most useful answer.
